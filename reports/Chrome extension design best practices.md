# Keep avow small, verifiable and honest

The best design for avow is the one it already has, tightened rather than expanded: a single static MV3 content script on `https://play.google.com/console/*`, no `permissions`, no service worker, no storage, an in-page panel in a closed shadow root, and filling that starts only on an explicit click. The research points to three places where that design is weaker than it looks. First, **the publisher account is a bigger risk than avow's code**: every major extension compromise found, from 2017 to the Cyberhaven campaign in December 2024, came through a phished developer account that pushed a malicious auto-update, and a hijacked extension with Play Console host access could read or change a developer's declarations. Hardware-key 2FA and Verified CRX Uploads close that path. Second, **`fill.js` currently reports "filled" without reading the control back**, and `element.click()` produces an untrusted event that some Google surfaces ignore. For a tool whose output is an audit trail, over-reporting success is the dangerous failure. Third, **the extension cannot be uploaded today**: the manifest has no `icons` key, which the Chrome Web Store requires. Most of the remaining work is small: WCAG 2.2 fixes inside one shadow root, a one-page privacy policy, listing copy that avoids Google trademarks as a name or logo, an allowlist zip script, and a dependency-free end-to-end test that exercises the real `matches` pattern. The prioritized backlog at the end splits this into PR-sized code tasks and manual dashboard or account tasks.

## A one-host content script is the narrowest grant, and the warning is honest

"No permissions" does not mean "no install warning". Chrome treats `content_scripts.matches` as host access, and adding or widening those patterns triggers a warning ([Chrome: Declare permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)); Chromium's own docs say scriptable hosts are messaged the same way as explicit host permissions ([Chromium permissions.md](https://chromium.googlesource.com/chromium/src/+/HEAD/extensions/docs/permissions.md)). Users should expect a single-host warning along the lines of "Read and change your data on play.google.com". The exact string was not confirmed from a primary source, so the packed extension should be test-installed to see it.

The alternative, `activeTab` plus `scripting`, shows **no install warning** and injects only after a user gesture ([Chrome: activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)). It costs a toolbar action, a service worker, a `permissions` entry and handling of clicks on non-Console pages, and it breaks the "nothing but a content script" story. The warning avow shows is accurate (it does read and change Console data), the scope is one host, and Chrome already lets any user restrict an extension to "on click" site access without code changes ([Chrome: User controls for host permissions](https://developer.chrome.com/docs/extensions/mv2/runtime-host-permissions)). Keep the static script and say in the listing that "on click" is available. One rule follows: **never widen `matches` in an update**, because widening re-prompts users and can disable the extension until they re-consent ([Chrome: Update your item](https://developer.chrome.com/docs/webstore/update)).

The same reasoning settles the side panel question. A side panel never overlaps the Console and its `sidePanel` permission carries no warning ([Permissions list](https://developer.chrome.com/docs/extensions/reference/permissions-list)). But it needs an `action`, a panel script and `tabs.sendMessage` to the content script, which still does all the DOM work, and Chrome messaging JSON-serializes payloads so a `File` cannot be passed directly ([Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging)). The popup is wrong outright, because it closes when focus moves to the page. Stay in-page and fix the collisions described below. Revisit the side panel only if the panel keeps fighting the Console's layout. Two manifest additions are worth making because they cost no permission: an `icons` key and `action.default_icon` with `default_title` ([chrome.action](https://developer.chrome.com/docs/extensions/reference/api/action)).

## The real security risks are the publisher account and mis-clicks

Content scripts run in an isolated world: the page cannot see avow's variables, but **the DOM is shared** ([Chrome: Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)), and Chrome's security guidance says to treat content-script inputs as possibly attacker-crafted ([Chrome: Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure)). A closed shadow root returns `null` from `host.shadowRoot` ([MDN: ShadowRoot.mode](https://developer.mozilla.org/docs/Web/API/ShadowRoot/mode)), but the page can still see, remove, restyle or overlay the host element. Treat it as style isolation, not secrecy. Play Console is Google's own page, so a hostile page is unlikely. A Console redesign or A/B variant that reorders options or changes labels is likely, and it produces the same failure: a wrong click. The same defenses handle both cases. Match on label text and structure, refuse when a match is ambiguous, click only `input[type=radio|checkbox]` or their `role` equivalents inside a recognised question block, and never click buttons, links or anything labelled save, submit, discard or publish. `fill.js` already follows the allowlist (its `RADIOS` and `CHECKBOXES` selectors) and refuses ambiguous per-type headings.

The gap is verification. `element.click()` dispatches an event with **`isTrusted: false`** ([W3C bug 25504](https://www.w3.org/Bugs/Public/show_bug.cgi?id=25504)). One project reports that Google Payments forms ignore untrusted clicks ([chrome-use commit](https://gitea.oimcloud.myaddr.tools/oimwiodev/chrome-use/commit/5a858af93f5d60d1ffce2c79bea6ac0f0d8669fb)). That is a single report, and whether Play Console's Material controls check `isTrusted` has to be tested live. Today `fillPage` and `fillCheckboxes` call `option.node.click()` and then mark the block green with no readback. The fix is cheap: after each click, read `checked` or `aria-checked` again and report each item as applied, already set, or not applied. Do not "upgrade" to trusted input through the `debugger` permission. It brings a severe warning and extra review scrutiny, and fixes nothing an honest "not applied" would not.

Injection hygiene is mostly in place. The panel's `innerHTML` in `panel.js` is a static template with no interpolation, and all dynamic text goes through `textContent`, which is the pattern Chrome recommends ([Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure)). A page's Trusted Types policy does not govern Chrome isolated worlds ([W3C Trusted Types wiki](https://github.com/w3c/trusted-types/wiki/Effects-of-deploying-Trusted-Types-on-browser-extension-developers)), so nothing on the Console side would catch a future mistake. Building the template with DOM calls instead lets `test/extension.js` ban `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `eval` and `new Function` outright, with no exceptions to maintain. `readManifest` already parses with `JSON.parse` and checks the top-level shape. It lacks a file-size cap before `file.text()`, and file strings must never become selectors. Manifest values should only choose among answers defined in code, which also keeps avow clear of the Web Store's ban on interpreters for remote commands ([CWS: MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)).

None of this protects against the dominant threat. In December 2024 a Cyberhaven employee was phished through a fake "CWS Developer Support" email into authorizing a malicious OAuth app, which published a poisoned update; the campaign hit at least 35 extensions and about 2.6M users, by secondary estimates ([BleepingComputer](https://bleepingcomputer.com/news/security/new-details-reveal-how-hackers-hijacked-35-google-chrome-extensions)). The pattern goes back to the 2017 Web Developer hijack ([The Register](https://www.theregister.com/2017/08/02/chrome_web_developer_extension_hacked/)). A malicious avow update that kept the same `matches` would trigger no new warning. Chrome recommends 2FA "preferably with a security key" ([Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure)). **Verified CRX Uploads** (since May 2025) reject any upload not signed with your private key, "even if your account or publishing workflow is compromised", and the extension ID stays the same ([Chrome blog: Verified uploads](https://developer.chrome.com/blog/verified-uploads-cws)). If API publishing is automated later, note that it fails with `PKG_MUST_UPDATE_AS_CRX` until one signed CRX has been uploaded by hand ([chromium-extensions thread](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/SybCdMk2LIE)). Keep the signing key off the machine that holds the dashboard session.

## Store policy is easy to satisfy if the listing says exactly what the code does

avow meets the single-purpose rule ([Program Policies](https://developer.chrome.com/docs/webstore/program-policies/policies)), and with no permissions an unused-permission rejection (Purple Potassium) cannot happen. The one ambiguity is privacy. Google's FAQ counts "website content" as user data and says disclosure applies "even when data is processed or stored locally" ([User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)). Read strictly, avow "uses" Console content. No source settles whether a script that only reads the DOM to click needs a policy, and a missing one is the Purple Lithium rejection ([Troubleshooting](https://developer.chrome.com/docs/webstore/troubleshooting)). A one-page policy removes the question: nothing collected, transmitted, stored or sold; the page and the JSON file are processed in memory on the device; plus the affirmative Limited Use statement the policy requires ([Limited Use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)). In the Privacy practices tab, give the single-purpose sentence, choose "No, I am not using remote code", leave the data types unticked and keep everything consistent with the policy ([Privacy tab](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy)). The data-minimization rules enforced from August 1, 2026 ([CWS policy updates 2026](https://developer.chrome.com/blog/cws-policy-updates-2026)) do not bite on an extension that collects nothing, but they also add a duty to tell users proactively if data handling changes. That is one more reason to refuse telemetry, even opt-in.

Branding is where an honest tool can still be rejected. The guidelines forbid Google trademarks, or confusingly similar marks, as the name or logo, and allow "for", "for use with" or "compatible with" plus ™ and an attribution line ([CWS Branding](https://developer.chrome.com/docs/webstore/branding)). "Google Play" is on Google's trademark list, and that list is non-exhaustive ([Google trademark list](https://about.google/brand-resource-center/trademark-list/)). Keep the name "avow", put "for Google Play Console™" in the summary and description with the attribution line, add "Not affiliated with or endorsed by Google", and keep the Play triangle and Google's four colors out of the icon. Unaltered Console screenshots are allowed for illustration. The current manifest `description` (101 characters, under the 132 limit) says "Play Console" without "Google" or ™, which is fine in the manifest and should get the full "for Google Play Console™" phrasing in the listing.

Listing requirements are modest: name of 75 characters or fewer, summary of 132 or fewer, a detailed description that opens with what the item does, a category, a 128x128 icon and at least one 1280x800 screenshot ([Listing docs](https://developer.chrome.com/docs/webstore/cws-dashboard-listing); [Images](https://developer.chrome.com/docs/webstore/images)). The 440x280 small promo tile is optional but matters: "Extensions without a small promo image appear after those that have one" ([Images](https://developer.chrome.com/docs/webstore/images)). The realistic rejection risks are thin metadata (Yellow Zinc), a listing that does not match behavior (Red Nickel) and "doesn't work" (Yellow Magnesium). The last one is the trap for avow, because a reviewer probably has no Play Console app to test on. Ship a sample manifest, test instructions and a short demo video. Reviews usually take a few days and can take a few weeks, with extra scrutiny for new developers ([Review process](https://developer.chrome.com/docs/webstore/review-process)). The account itself needs the one-time US$5 fee ([Chromium Blog](https://blog.chromium.org/2020/03/new-developer-dashboard-and.html?m=0)), mandatory 2-Step Verification ([2SV policy](https://developer.chrome.com/docs/webstore/program-policies/two-step-verification)), a developer email that can never be changed ([Register](https://developer.chrome.com/docs/webstore/register)) and a trader or non-trader declaration under the EU DSA ([Trader FAQ](https://developer.chrome.com/docs/webstore/program-policies/trader-verification-faq)). A free MIT project naturally fits non-trader, which keeps an address and phone number off the listing.

## The panel's accessibility gaps are small fixes inside one shadow root

The panel sits at `right: 16px; bottom: 16px` with `max-height: 60vh`, the same corner as the Console's sticky Save bar. WCAG 2.2 SC 2.4.11 (AA) names "sticky footers ... and non-modal dialogs" as typical causes of obscured focus, and says a persistent overlay passes if a dedicated keyboard command, such as Escape, hides or collapses it ([W3C Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)). Collapse on Esc, collapse to a small pill after a fill, and offer a top-right dock held in memory. Writing state to `localStorage` would write to Google's origin and is already banned by the test. Showing the host with `popover="manual"` puts it in the top layer and retires the `z-index: 2147483647` hack; the Popover API is Baseline 2025 ([MDN Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using)).

The other gaps line up with specific success criteria. `#status` and `#result` have no live-region role, so "Filled N" is never announced. Use `role="status"` for results and `role="alert"` for parse errors, and avoid `aria-live="assertive"` on non-urgent text, which the W3C lists as a failure ([W3C Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). The jump rows are `<li class="jump">` with a click handler, so they cannot be reached by keyboard. Chrome's own a11y guidance says to prefer native controls ([Chrome: Accessibility](https://developer.chrome.com/docs/extensions/how-to/ui/a11y)), so make them `<button>`s that scroll to the question and focus its first control. ARIA IDREFs cannot cross shadow roots ([Nolan Lawson](https://nolanlawson.com/2022/11/28/shadow-dom-and-accessibility-the-trouble-with-aria/)), so focus has to move programmatically. The toggle keeps a static `aria-label="Collapse"` and needs `aria-expanded` and `aria-controls`. In forced-colors mode `box-shadow` becomes `none` and every outline color collapses to one system color ([MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)). That leaves the solid versus dashed outline as the only cue on page blocks. Add a short visible text tag on each marked block and replace green and yellow (`#1e8e3e` and `#f9ab00`), a weak pair for deuteranopia, with something like blue and orange. That pairing is a design judgment, not a sourced rule. Add a `prefers-color-scheme: dark` token block, swap `behavior: "smooth"` for `"auto"` under `prefers-reduced-motion`, and give the panel its own accent so it never reads as a Console dialog.

Two behaviors keep the panel truthful on a single-page app. Play Console route changes do not reload the document, so the `document_idle` injection fires only once ([Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)), and outlines and results go stale. The Navigation API's `currententrychange` and `navigatesuccess` events (Baseline 2026) are a cheap signal to clear marks and say "Page changed, fill again" ([MDN Navigation API](https://developer.mozilla.org/en-US/docs/Web/API/Navigation_API)). That they fire inside an isolated world is inferred, not documented, so check it live. Do not leave a `subtree: true` observer on `document.body`, since it produces a notification for every descendant change ([MDN observe](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver/observe)). Also, matching is by English text, so a Console set to another language silently finds nothing. Check `document.documentElement.lang` and say "English Console only" instead of "No questions avow knows were found". Whether the Console sets `lang` reliably is unverified. Finally, put each yellow reason in the visible list (it already is) rather than in a `title` tooltip that keyboard and touch users cannot reach, and turn the empty state into three numbered steps so onboarding needs no storage.

## Icons, packaging and tests can all stay dependency-free

Chrome wants square PNG icons at 16, 32, 48 and 128 under `icons`. SVG is rejected for every manifest icon, and with no icon Chrome generates a letter ([Configure icons](https://developer.chrome.com/docs/extensions/develop/ui/configure-icons)). The toolbar icon takes 16, 24 and 32 under `action.default_icon` ([chrome.action](https://developer.chrome.com/docs/extensions/reference/api/action)). The 128px store icon holds about **96x96 of artwork inside transparent padding**, has to work on light and dark backgrounds, and should have no border or large shadow ([Images](https://developer.chrome.com/docs/webstore/images)). At 16px, align strokes to whole pixels and check the icon at real size ([Volvo Cars icon construction](https://design.volvocars.com/icons/construction/)). A concept that survives 16px: a rounded square in one saturated non-Google hue (deep indigo or teal) with a heavy white check whose stroke is a whole pixel count at every size, and an optional speech-bubble tail ("declare") at 128 only. Keep a hand-written `icon.svg` as the source, export the PNGs once on a dev machine, hand-tune the 16px file and commit the PNGs, so neither CI nor the package gains a tool. `test/extension.js` can then check each PNG's dimensions against its manifest key with the existing `src/lib/imagesize.js`. For screenshots, use 1280x800 captures from a demo app with account names hidden. The store downscales them to 640x400, so zoom the browser until panel text stays legible ([Images](https://developer.chrome.com/docs/webstore/images)).

Packaging needs `manifest.json` at the zip root, not in a folder, and `icons` is a required field ([Prepare](https://developer.chrome.com/docs/webstore/prepare)). An allowlist zip of `manifest.json`, `src/` and `icons/`, built from inside `extension/` into `dist/`, keeps the README and any fixtures out. Running `git archive` from a tag makes the zip reproducible, so anyone can diff the store package against the repo. Ship code as authored. Obfuscation is banned (Red Titanium), and minification is allowed but slows review ([Review process](https://developer.chrome.com/docs/webstore/review-process)). `version` takes one to four integers from 0 to 65535, so `0.2.0-beta.1` is invalid. Express a beta as `0.2.0.1` and put the label in `version_name` ([Manifest: version](https://developer.chrome.com/docs/extensions/reference/manifest/version)). Every upload must carry a higher version than the last. Leave `minimum_chrome_version` unset unless a test proves an API needs it, because users below the minimum stop receiving updates silently ([minimum_chrome_version](https://developer.chrome.com/docs/extensions/reference/manifest/minimum-chrome-version)). Separate `ext-v*` tags let the CLI and the extension release independently.

On testing, the existing `test/extension.js` is a good unit layer: it runs the four scripts in `vm`, bans network, storage and submit APIs, and forbids permission keys. But it never loads the extension into a browser, so nothing checks `matches`, script order or behavior against a DOM. Branded Chrome 137+ ignores `--load-extension`, while Chromium and Chrome for Testing still honor it ([chromium-extensions PSA](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY/m/S0ET5wPjCAAJ)), and extensions load only in new headless mode ([Chrome: E2E testing](https://developer.chrome.com/docs/extensions/how-to/test/end-to-end-testing); [Chrome Headless](https://developer.chrome.com/docs/chromium/headless)). A dependency-free route: spawn Chrome for Testing with `--headless=new --load-extension`, have CDP `Fetch` serve fixture HTML for `https://play.google.com/console/...`, and drive it with Node's built-in `WebSocket`. That exercises the real match pattern without touching Google. This route has not been verified end to end. The global `WebSocket` needs Node 22, while `package.json` declares `>=20`, so make it a separate opt-in script rather than part of `npm test`. Puppeteer's `enableExtensions` ([Puppeteer guide](https://pptr.dev/guides/chrome-extensions)) would be simpler, but it is a dependency and would need the `ARCHITECTURE.md` justification the project requires. Performance needs little work. `document_idle` is the default and right choice, and avow scans only on click, so its idle cost is mounting one small panel.

## Conclusion

The research reverses the usual priority order for extension hardening. avow's code surface is so small that its own bugs are mostly about honesty: claiming a fill that did not happen, or giving up silently on a non-English Console. The threats that could actually hurt a developer sit outside the code, in the publisher account and the release path. That is why account security and verified uploads come before any further code hardening, and why the one code change in P0 is a readback, not a new defense.

The project's own principle carries over directly to the extension. store-decl fails CI when the manifest contradicts the code, and every claim in the avow listing ("no permissions, no network, nothing stored, never submits") can be enforced the same way by `test/extension.js`. If each trust line in the listing maps to a test, the listing cannot drift from the code, which removes the main source of misleading-listing rejections and tells users why they can believe it. Three facts still need a live check before release: the exact install warning text, whether Play Console controls accept untrusted clicks, and whether Navigation API events reach the isolated world.
